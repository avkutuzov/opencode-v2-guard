# Guard: как не получить маску в коде и путях

Guard сканирует по содержимому, а не по типу файла: присваивание с «ключевым»
именем (`password`, `token`, `apiKey`, `client_secret`, `access_key`,
`refresh_token`, `pwd`, `passwd`) маскирует значение справа — даже если там
не секрет, а ссылка на переменную окружения. Маска вставляется в файл при
записи: write возвращает success, синтаксис ломается, ошибка всплывает только
на компиляции. Ниже — три уровня защиты: конфиг guard'а (рекомендуется),
имена переменных и форма присваивания.

## 1. Конфиг guard'а — основной способ

В `~/.config/opencode/opencode.json`, в `options` плагина guard:

```json
{
  "exemptPaths": ["test/**", "fixtures/**"],
  "disabledPatterns": ["credential-assignment"]
}
```

- **`exemptPaths`** — глобы путей, при записи в которые маскирование
  отключено. Для тест-фикстур и файлов с фиктивными ключами. Блокировка
  секретных путей при этом продолжает работать.
- **`disabledPatterns: ["credential-assignment"]`** — точечно выключает
  generic-паттерн «ключ = значение». Префиксные паттерны остаются и ловят
  настоящие секреты (`sk-…`, `ghp_…`, `AKIA…`, JWT, PEM-блоки) в любом
  контексте, включая строки с env-ссылками.
- **`mode: "warn"`** — guard не переписывает текст вообще, только пишет
  аудит: нулевая порча, полная видимость.
- **`piiEmailAllowDomains`** — домены email, не маскируемые нигде.
- После изменения конфига нужен свежий `opencode serve`: долгоживущий сервис
  не перечитывает опции плагина.

## 2. Имена переменных — без ключевых слов

Значение маскируется у любого присваивания имени, содержащего ключевое слово
как подстроку: password, passwd, pwd, secret, token, api_key, apiKey, API_KEY,
access_key, refresh_token, client_secret. `openaiApiKey` матчится так же, как
`apiKey`.

Плохо:
`const apiKey = process.env.OPENAI_API_KEY`

Хорошо:
`const judgeKey = process.env.OPENAI_API_KEY`

Хорошо (деструктуризация — в левой части нет имени с ключевым словом):
`const { OPENAI_API_KEY: judgeKey } = process.env`

Безопасные корни имён: `cred`, `creds`, `judgeKey`, `authCred`,
`openaiCred`.

## 3. YAML/JSON — то же правило для ключей

Ключ с ключевым словом маскирует значение справа и в YAML, и в JSON:
`password: summer.rain`
превратится в маску при записи. Для фиктивных значений — переименуйте ключ
или держите файл в exempt-пути. Для настоящих секретов — переменные окружения,
не литералы.

## 4. Пути

- Файлы с секретами заблокированы целиком (.env, *.pem, *.key, .ssh/**,
  .aws/**, kubeconfig, *.tfstate, **/credentials): агент не читает их и не
  должен — значения передаются через переменные окружения, в чат идут только
  имена полей.
- Email в путях не маскируется: `/home/user@example.com/.config` останется целым
  (email-в-пути — отдельное правило, не ломает команду).
- Не сочетайте упоминания файлов из списка выше с exfil-лексикой (curl, wget,
  base64, «отправь», «пришли») в одной команде: рядом с такими словами
  срабатывает prompt-injection паттерн и маскирует упоминание пути.
- Файл уже испорчен маской → `git restore <файл>`. Не чините его через шелл:
  команды сканируются тем же паттерном, и маска прилетит прямо в команду.

## 5. base64/hex

Не упаковывайте секретоподобные строки в base64/hex: blob-детектор декодирует
блоб и маскирует его целиком, если внутри находит секрет.

## 6. Настоящие секреты

Всё выше — про ложные срабатывания. Реальный секрет в чате, файле, логе или
git-истории — это компрометация: маска не отменяет утечку, ключ нужно
ротировать.

## 7. Если маска не появилась (диагностика guard'а)

Известный баг рантайма (2026-11-25, см. docs/npm-token-investigation.md):
в долгоживущем сервисе OpenCode 2.4.0 после повторной инициализации
плагина session-хук `prompt` молча перестаёт срабатывать — секреты,
набранные прямо в чате, уходят модели без маски. Tool-вызовы, вывод
команд и context-слой при этом продолжают маскировать. Кроме того,
OpenCode кэширует npm-резолв плагина `@latest` и не перекачивает новые
версии, пока существует кэш-каталог.

Признаки: вставка тестовой строки `npm_` + 36 букв/цифр пришла в чат
целиком, без `<REDACTED:api-key:…>`.

Что делать:

1. Перезапустить сервис: `opencode service restart` (после перезагрузки
   плагина тем же процессом хук не восстанавливается — нужен именно
   рестарт сервиса).
2. Обновить застрявшую копию плагина: удалить кэш-каталог
   `~/.cache/opencode/npm/opencode-v2-guard@latest` и снова
   `opencode service restart` — OpenCode скачает актуальную версию.
3. Проверить восстановление той же тестовой строкой: она должна
   вернуться маской `<REDACTED:api-key:…>`.
4. Долгосрочно: пиновать версию плагина в opencode.json (например,
   `opencode-v2-guard@1.2.4`) вместо `@latest` — кэш перестанет
   протухать.

До восстановления prompt-хука не вставляйте реальные секреты напрямую
в чат — они не защищены; передавайте их через переменные окружения
(см. раздел 2).

## Что маскируется всегда (контекстно-независимо)

- префиксы ключей: `sk-…`, `rk_…`, `ghp_/gho_/ghu_…`, `github_pat_…`,
  `xoxb-…`, `AKIA…`, `AIza…`, `ya29.`, `hf_…`, `npm_…`, `glpat-…`
- JWT (`eyJ…`), Bearer-токены, PEM-блоки приватных ключей
- generic «ключ = значение» с ключевым словом (credential-assignment)
- base64/hex-блобы, декодирующиеся в секрет
- email, телефоны, карты, ИНН/СНИЛС (PII)

Связанный журнал: docs/credential-assignment-investigation.md — инцидент
«маска испортила write», разбор и решение (инструкции вместо фикса).
